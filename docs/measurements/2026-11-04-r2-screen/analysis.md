# 분석 노트 — 2026-11-04 R2 선곡 프롬프트 스크리닝 (1·2회차)

## 목적과 조건

R2는 LLM이 곡을 직접 고르는 프롬프트를 운영 계약으로 만드는 단계다. 후보 수정을 하나씩 누적한 변형 V0~V4를 같은 입력으로 비교해, 어떤 수정이 효과가 있는지 가렸다.

- 입력: `docs/measurements/eval/holdout-inputs.json` 40개. R5 최종 비교용 `inputs.json` 26개는 프롬프트 튜닝에 쓰지 않는다
- 모델: gpt-6-luna, `reasoning_effort: none`. 변형 정의는 `apps/backend/src/openai/pick-prompt.ts`의 `PICK_VARIANTS`(커밋 `cec89c7`). 프로브는 운영 빌드의 프롬프트·스키마를 그대로 읽는다
- 해석: 프로브 `resolve`(분당 15회), 운영 해석기 v2.1
- 1회차(이 폴더): V0~V4 × 40입력, 오류 0
- 2회차(`2026-11-04-r2-rep2`): 1회 측정의 흔들림이 ±5%p 정도라(거의 같은 프롬프트인 11/3 A0 60% vs V0 55%) 후보 V3·V4만 한 번 더 재고 **두 회차 평균으로 판정**했다. 좋은 회차만 고르지 않는다

**측정 전에 고정한 합격 기준(11/4)**

- 감정 일치: V0 대비 회귀 없음(문맥 함정 4/4 유지, 명확·애매 각각 −1 이내)
- 완화 모드 상위 20곡 비율 ≤ 35% — 출발점(A0) 60%, 심취 모드는 26~28%
- 처음 보는 곡(11/2 튜닝 547곡에 없던 곡) 해석률 ≥ 85%, 모드 10곡 채움 ≥ 75/80

## 3. 2회차와 판정

| 기준 | V3 1회 / 2회 | V4 1회 / 2회 | 합격선 |
| --- | --- | --- | --- |
| 감정 명확·애매 / 함정 | 34 / 34 · 4/4 / 4/4 | 34 / 34 · 4/4 / 4/4 | ✓ |
| 처음 보는 곡 해석 | 96% / 97% | 93% / 96% | ✓ |
| 모드 10곡 채움 | 80 / 80 | 79 / 77 | ✓ |
| 완화 상위 20곡 | 39% / 37% → **평균 38%** | 37% / 43% → **평균 40%** | ✗ (≤35%) |
| 완화 중 회피 목록 곡 · Jaccard | 1% / 1% · .067 / .063 | 1% / 0% · .063 / .083 | — |

- **판정: 두 변형 모두 완화 쏠림 기준 미달.** 나머지 기준은 통과했다. 기준을 바꾸거나 회피 목록을 늘려 숫자를 맞추지 않고 미달로 기록한다 — 목록을 늘리면 다음 기본곡으로 옮겨 갈 뿐이라는 것이 이 측정의 관찰이다
- 네 번 측정 모두 완화 1위는 `Sunrise`(40응답 중 25~30, 12개 감정 중 10개)
- V4는 두 회차 차이(37 ↔ 43%)가 사고 필드 효과보다 크고 곡 앞 출력이 길어 **운영 후보는 V3**
- 지연은 판정하지 않았다. 같은 프롬프트(A0)가 11/2 6.2s, 11/3 4.0s로 날짜 차이가 변형 차이보다 크고, 2회차는 네트워크 오류(아래)로 오염됐다. 지연은 R5에서 첫 곡 ≤2.5s · 전체 ≤8s 기준으로 잰다

## 4. 다양성 진단 — 무엇이 반복되는가

V3 두 회차로 반복의 위치를 나눠 봤다.

| 관점 | 값 | 해석 |
| --- | --- | --- |
| 같은 입력을 두 번 | 완화 22% · 심취 36%만 같은 곡 | 요청 간 변동은 이미 크다 |
| 다른 감정끼리 완화 | 평균 12% 겹침(12곡 중 ~1.4곡), 같은 감정끼리 20% | 대부분은 감정마다 다르다 |
| 6개 이상 감정에 나온 곡의 자리 | V0 53% → V3 24~28% | 감정 무관 반복은 절반 이하로 줄었다 |

남은 문제는 목록 전체가 아니라 **감정과 상관없이 거의 매번 끼는 소수의 머리 곡**이다. 상위 20곡 비율은 같은 감정 안의 반복(슬픔 입력 세 개에 같은 위로곡)까지 쏠림으로 센다는 한계도 확인했다.

## 5. 해석 실패 원인 — 실존하는 유명 곡을 못 찾는 이유

두 회차를 합친 해석 실패 고유 곡은 82곡이다(한글·일본어 곡명 57, 한글 아티스트 + 영문 곡명 9, 영문 16). 대표 곡을 iTunes에 직접 다시 물어 원인을 확인했다(11/5, 약 25회 호출).

1. **검색 API가 explicit 곡을 돌려주지 않는다.** `explicit=Yes`를 줘도 같다.
   - Green Day `American Idiot`, Alanis Morissette `You Oughta Know`, Bon Iver `Holocene` 모두 검색 25위 안에 원곡이 없고 자장가·현악 커버가 상위를 채운다. Green Day 검색 결과 25건은 전부 notExplicit였다
   - Green Day 앨범 lookup과 Bon Iver 아티스트 lookup에서는 원곡이 explicit 표기로, 미리듣기와 함께 있다
2. **한국 곡은 US·KR 스토어의 trackId가 다를 수 있다.** US 검색은 `Time of Our Life / DAY6`, `Gangnam Style / PSY`, `DALLA DALLA / ITZY`를 1위로 찾지만, 그 ID를 KR 스토어에서 lookup하면 0건이다. 그래서 한글 곡명과 대조할 표기를 얻지 못한다. KR 스토어 검색은 11/3부터 결과가 항상 0건이라 대안이 되지 않는다
3. **아티스트 표기 차이.** LLM은 `자이언티`·`지코`로 쓰지만 KR 스토어도 `Zion.T`·`ZICO`로 표기한다. 곡명(`양화대교`·`아무노래`)은 KR lookup으로 맞았다
4. (드묾) V0 한 응답에서 아티스트·곡명이 뒤바뀐 4곡

실패 82곡 중 약 30곡(수작업 분류)이 아이돌·힙합·록 곡이다. 해석 사각지대가 결과를 발라드·어쿠스틱 쪽으로 기울게 만든다는 점에서 이것도 다양성 문제다.

**우회 확인**: 아티스트 ID로 곡 목록을 조회하면(`lookup?id=<artistId>&entity=song&limit=200`) 세 곡 모두 나왔다. Green Day(US, explicit 원곡), DAY6(KR, `한 페이지가 될 수 있게 / 데이식스`), PSY(KR, `강남스타일 / 싸이`)다. 검색이 실패했을 때만 부르면 추가 호출은 실패 건당 1~2회다.

## 6. 결론과 다음

- 운영 후보는 V3. 완화 쏠림은 기준 미달(38%)로 남긴다
- 프롬프트로 특정 곡을 금지하면 모델 분포가 옮겨 갈 뿐이다. 다음 단계에서는 LLM 출력은 두고 서버가 **보여주는 순서만** 바꾼다
  - 최근 응답에 자주 나온 곡과 이 사용자가 이미 본 곡을 뒤로 민다
  - 완화 모드는 15곡을 골라 뒤로 밀 여유를 만든다
- 그 단계부터 다양성 합격은 **화면에 보인 10곡**으로 잰다(상위 20곡 ≤35%, 가장 자주 나온 한 곡 ≤ 완화 목록의 25%). LLM 후보를 세면 서버가 순서를 바꾼 효과가 숫자에 나타나지 않기 때문이다. 같은 방식으로 지금 V3를 다시 세면 40% / 39%다
- 해석기는 검색 실패 시 아티스트 곡 목록을 조회하는 단계를 더한다(v2.2)
