# 추천 품질 평가 (eval)

추천 재설계 **전후를 같은 조건으로** 비교한다. 지표와 조건은 측정 전에 이 문서로 고정하고, 바꿀 땐 이유와 날짜를 남긴다.

## 하네스 목록과 원칙 (2026-11-11)

| 하네스 (`apps/backend/scripts/eval/`)                  | 묻는 것                                                               | 방식                                                                                                         |
| ------------------------------------------------------ | --------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------ |
| `probe-picks.cjs`                                      | LLM 선곡의 감정 판정 · 해석률 · 쏠림(다양성) · 지시 준수              | 선곡(pick)과 해석(resolve, 분당 15회)을 나눠 프로세스 안에서. 운영 빌드의 프롬프트·해석기를 그대로 쓴다      |
| `probe-latency.cjs` (+ `net-tap.cjs` · `net-mock.cjs`) | 사용자가 받는 것: 첫 곡 · 전체 시간, 외부 호출 수, 화면 곡 · 감정(R5) | 서버를 띄워 HTTP로. 바꾸기 전 빌드를 얼려 같은 실행에서 번갈아 부른다 — 아래 "응답 시간 하네스"              |
| `blind-sheet.cjs`                                      | 블라인드 무드 적합도(R5)                                              | 기준선 · R5 화면 곡으로 라벨 없는 평가 시트를 만들고, 매긴 점수를 열쇠와 맞춰 집계한다 — 아래 "R5 최종 비교" |
| `summarize.cjs`                                        | 11/2 기준선 요약                                                      | 결과 파일만 읽는다(기준선 하네스는 R4에서 삭제)                                                              |
| `mock-adapter.cjs`                                     | —                                                                     | `probe-picks --mock`의 iTunes 흉내                                                                           |

7월 응답 시간 스크립트(`docs/measurements/2026-07-21-response-timing/measure*.{sh,mjs}`)는 아티스트 기반 시절 기록이라 지금 서버에는 맞지 않는다(보관용).

- **질문 하나에 하네스 하나** — 선곡 자체(probe-picks)와 사용자가 받는 결과(probe-latency)는 따로 잰다
- **잰 것 = 배포하는 것** — 운영 빌드(`dist`)의 프롬프트·스키마·해석기를 그대로 쓴다. 측정 전 `npm run build`
- **빈 상태에서 시작** — 응답 시간은 서버를 매번 새로 띄운다(곡 해석 캐시 6시간). 시간대에 따른 LLM 속도 변동은 같은 실행에서 번갈아 불러 상쇄한다
- **입력은 파일로 고정** — `inputs.json` · `holdout-inputs.json`, 섞을 땐 고정 시드. 쓴 입력 파일(과 sha1)은 meta에 남긴다
- **결과 폴더 규약** — `docs/measurements/<날짜>-<라벨>/` = `meta.json`(커밋 · 옵션 · 모델 · 변형 · 곡 수) + 원자료 + `summary.md`. 다시 요약하는 데 필요한 값은 meta에 남겨 운영 코드가 바뀌어도 요약할 수 있게 한다(11/11: probe-picks 요약은 모드별 곡 수를 운영 코드가 아니라 meta에서 읽는다)
- **단, probe-picks 요약의 "D3 후순위" 표는 지금 운영의 순서 규칙(곡 키 · 빌리기)으로 다시 재생한다** — 규칙이 바뀌면 예전 폴더를 다시 요약한 결과도 달라진다. 커밋된 `summary.md`는 그 측정 시점 코드의 출력이다. 재생은 입력 파일 순서를 따르므로 같은 입력 파일이 있어야 같은 결과가 나온다
- **키 없는 자체 검증** — 하네스마다 `--mock` 경로를 둔다. 실제 API 실행은 사용자가
- **측정 중 repo 수정 금지**, iTunes를 부르는 실행은 동시에 하나
- **걷어 낸 하네스·옵션은 마지막으로 들어 있던 커밋을 적는다** — 기준선 하네스 `run.cjs`·`instrument.cjs` → `56dd4dd` · probe-picks의 모델 비교(gpt-4.1-mini · gpt-6.1-terra)와 `--reasoning` → `b0e6760` · 선곡 변형 V0~V4(플래그 6개)와 probe-picks `--variants` → `ed3ebaf` (11/11 R5 뒤 V5로 고정, 이후 기록의 변형 칸 = `PICK_PROMPT_VERSION`)

## 대상

- 기준선: 앱 코드 커밋 `e4cda32` (캐시·필터 수정, 의존성 보안 업데이트, 포맷 정리 반영 후 · 재설계 전). 하네스·입력 파일은 이후 커밋에 추가되지만 앱 코드(`apps/*/src`, `packages/`, lockfile)는 바뀌지 않는다
- 재측정: 재설계 단계마다 같은 입력·조건으로
- 기준선 하네스(`apps/backend/scripts/eval/run.cjs`·`instrument.cjs`)는 Last.fm 경로를 감싸 재는 코드라 R4(11/9, Last.fm 경로 삭제)에서 지웠다. 재현은 하네스를 추가한 커밋 `56dd4dd`(앱 코드는 `e4cda32`와 같음)를 체크아웃해 아래 절차로 한다. `summarize.cjs`는 결과 파일만 읽으므로 남겨 두었다

## 입력

- `inputs.json` 26개 (12감정 × 명확/애매 + 문맥 함정 2). `repeat: true` 6개는 본 실행이 끝난 뒤 한 번 더 실행 (총 32회)
- 문맥 함정: 웃음 표기(ㅋㅋ·ㅎㅎ)처럼 표면 단서와 실제 감정이 어긋나는 입력 — 단서가 아니라 문맥으로 판단하는지 본다
- 실행 순서는 고정 시드로 섞는다 (감정 순서에 따른 throttle 편향 방지)

## 조건

- **프로세스 내 하네스**: 서버·컨트롤러·SSE를 거치지 않고 `EmotionService`를 직접 호출 → 전송 계층을 빼고 추천 파이프라인만 잰다. 앱 코드는 바꾸지 않는다
- 새 프로세스로 시작 (인메모리 캐시가 빈 상태). 실행 중 캐시는 실서비스처럼 유지
- 요청 간 **120초**
- 측정 중 repo 수정 금지 (결과에 기록한 커밋 해시와 실제 코드가 어긋나지 않게)
- 요청 단위 실패는 기록하고 다음 입력으로 진행
- API 키는 앱과 같은 방식(ConfigModule)으로 로드 — 실행은 사용자가 한다

## 합격 기준 (2026-11-04 고정)

- **지연**: 첫 곡 카드 ≤ 2.5초(스트리밍) **그리고** 요청 전체 ≤ 8초, 둘 다 p50. 이전 기준 "요청 전체 5초"는 LLM 응답만 4~6초(luna p50, 11/2·11/3 프로브)라 구조상 지킬 수 없어 바꿨다. 첫 곡 카드 시점은 아래 응답 시간 하네스(`probe-latency.cjs`)로 잰다
- **라벨 검토 `romance-clear`**: 기준선에서 모델 3개 모두 excited로 판정했지만 정답은 romance만 유지한다. 프롬프트 정의(romance = 설렘/사랑, excited = 신남/들뜸)상 대상이 분명한 설렘이고, "심장 터질 것 같아"는 표면 단서다 — 문맥 함정과 같은 기준

## 블라인드 지표 (6일차)

- **무드 적합도**: 원안은 입력별로 기준선·재설계 플레이리스트를 섞어 A/B로만 표시하고 모드마다 1~5점 + 선호 → 11/11 곡 단위 · 수 맞춤으로 바꿨다(아래 "R5 최종 비교")
- **모드 분리**: 무드 표현(valence·energy 등, 남은 결정 M6)을 정한 뒤 정의한다 — R5에서는 재지 않는다

## 응답 시간 하네스 (`probe-latency.cjs`, 2026-11-10)

위 품질 하네스와 질문이 다르다: **사용자가 첫 곡을 언제 보나 · 전체는 언제 끝나나 · 그동안 외부 호출이 몇 번인가**. 바꾸려는 것이 전송 방식(SSE → 스트리밍)이라 위 "프로세스 내 하네스" 조건 대신 실제 서버를 HTTP로 부른다.

- **서버는 하네스가 띄운다**: 실행마다 새 프로세스(캐시가 빈 상태에서 시작). 서버 로그(`[timing]`·`[serve]`)를 요청별로 함께 기록
- **외부 호출**: 서버에 `net-tap.cjs`를 끼워(`node -r`) iTunes·OpenAI 호출의 시작·헤더 도착·끝 시각과 상태를 기록한다. 운영 코드는 그대로이고, 검색어와 헤더(인증 키)는 남기지 않는다
- **전·후 비교 = 얼린 빌드 A/B**: 바꾸기 전 빌드를 `freeze`로 `apps/backend/.measure/<이름>/dist`에 얼리고(커밋 해시 기록, `dist` 규칙으로 git 무시), 바꾼 뒤 얼린 서버와 새 서버를 **같은 실행에서 번갈아** 부른다(입력마다 순서도 바꿈). LLM 속도의 시간대 변동(11/4 판정 불가의 원인)을 상쇄하려는 것
- **입력**: 기본 12개 = `inputs.json`에서 감정 순서대로 명확·애매를 번갈아 고른 것(12감정 한 번씩, 명확 6 · 애매 6, 문맥 함정 제외)을 시드 20261110으로 섞는다. `--ids`·`--inputs`로 바꿀 수 있다
- **간격**: 앞 요청이 끝난 뒤 120초. 요청마다 다른 `X-Real-IP`를 보내 요청 제한(IP당 분당 5회)에 걸리지 않게 한다 — 실제 사용자도 각자 따로 세어진다
- **첫 곡**: 곡이 담긴 첫 이벤트(응답)를 받은 시점. 전송 `stream`(POST 스트림)은 첫 `track` 이벤트, `sse`(옛 GET)·`post`(한 번에 받는 POST `/analyze`)는 곡이 완료 시점에 한꺼번에 와서 첫 곡 = 전체. 머리말(`meta` 이벤트: 감정·공감 문구·아트워크) 시점도 따로 기록한다
- **판정**: 합격 기준(위)의 p50, 같은 입력끼리 짝지은 차이의 중앙값
- 실행 (`apps/backend`에서, 실제 API — 사용자가):
  ```bash
  node scripts/eval/probe-latency.cjs freeze --as baseline       # 바꾸기 전, 커밋된 상태에서
  node scripts/eval/probe-latency.cjs run --label latency-base --servers baseline:sse --limit 6
  node scripts/eval/probe-latency.cjs run --label latency-ab --servers baseline:sse,current:stream   # 스트리밍 뒤 (npm run build 후)
  ```
  키 없이 자체 검증: `--mock --interval 0` — `net-mock.cjs`가 OpenAI·iTunes를 흉내 내고, 서버는 `.env`가 없는 빈 폴더에서 띄운다
- 산출물은 아래와 같은 폴더 규약(`meta.json`·`raw.jsonl`·`summary.md`)

## R5 최종 비교 (2026-11-11 고정)

기준선(11/2, gpt-4.1-mini · Last.fm 하이브리드)과 지금 운영(V5 · luna · 곡 단위 스트리밍)을 같은 입력 · 간격으로 비교한다. 측정 전에 고정하고, 바꾸면 이유와 날짜를 남긴다.

**실행** — `probe-latency.cjs`로 지금 빌드(`current:stream`)를 HTTP로 부른다. 기준선처럼 LLM → iTunes 해석 → 지역 쿼터 → 이력까지 실제 경로 전체를 지난다

- 입력: `inputs.json` 26개 전부(`--all`, 시드 20261110으로 섞음). 끝난 뒤 `repeat: true` 6개를 한 번 더(`--repeat`) — 총 32회, 요청 사이 120초
- 서버는 한 번 띄워 32회 내내 유지한다 — 곡 해석 캐시 · 전체 노출 창이 실서비스처럼 쌓인다
- 이력: 본 실행은 빈 이력(처음 온 사람). 반복 실행은 그 입력의 첫 화면 곡 키를 `seen`으로 보낸다 — 같은 사람이 같은 글을 바로 다시 쓴 경우(브라우저와 같은 방식)
- 기록: 응답 시간 하네스 항목 + 감정 · 화면 곡(모드별 곡명 · 아티스트 · 곡 키 · id)
- 실행 (`apps/backend`에서, 실제 API — 사용자가): `npm run build` → `node scripts/eval/probe-latency.cjs run --label r5 --servers current:stream --all --repeat`

**자동 지표** — 기준선 `2026-11-02-baseline/summary.md`와 나란히

- 감정 분류 일치율(명확 · 애매 · 문맥 함정 따로) · 수율(모드별 화면 곡 / 10) · 요청당 iTunes 호출 · 차단 · 지연 p50(기준선은 한 번에 받는 구조라 첫 곡 = 전체). 표는 본 실행 26회로 만든다
- 기준선은 서버 없이 서비스를 직접 불렀다(프로세스 내). R5는 HTTP를 거치지만 로컬이라 전송 몫은 작다
- 지역 구성 · 출처 · 시드 해석률은 비교하지 않는다(Last.fm 확장이 없고, 응답에 지역이 없다). 다양성(상위 20곡 등)은 응답 수가 다른 D4 판정(홀드아웃 40입력)과 섞지 않는다

**같은 글 다시 + 이력** (심취 15곡 판단)

- 반복 6입력의 두 번째 화면 10곡 중 첫 화면에서 본 곡 수, 모드별 평균
- 심취 평균이 3곡 이상이면 심취도 15곡(8/5/2)으로 늘리는 안을 응답 시간과 함께 다시 잰다. 출력이 3곡 늘어 전체 시간이 길어지므로 전환은 👤 결정. 11/9 운영 관찰: 심취(12곡) 5/10 · 완화(15곡) 0/10

**블라인드 무드 적합도 — 곡 단위 · 수 맞춤** (`blind-sheet.cjs`)

원안(목록 A/B + 선호, 위 "블라인드 지표")을 바꿨다(11/11): 기준선은 iTunes 차단으로 모드당 평균 1.9곡(심취 26개 중 11개가 0곡)이라, 목록을 나란히 놓으면 곡 수로 어느 쪽인지 드러난다.

- 묶음 = 입력 × 모드(본 실행만). 기준선 화면 곡 k개 + R5 화면 곡 중 고정 시드로 뽑은 k개를 섞는다. 기준선이 0곡인 묶음은 빼고 수율에서 보고한다. 같은 곡이 양쪽에 있으면 한 줄로 매기고 점수는 양쪽에 넣는다
- 시트에는 글 · 모드 · 곡(아티스트 - 곡명) · 들어보기 링크(`music.apple.com/kr/song/<id>`, 양쪽 같은 형식)만 둔다. 묶음 순서와 묶음 안 곡 순서는 고정 시드로 섞는다. 어느 쪽 곡인지(열쇠 파일)는 점수를 다 매긴 뒤에 연다
- 평가자: 사용자가 전부 매긴다(판정). Claude는 새 에이전트에 같은 시트만 주고 따로 매긴다(일치도 확인 — 저장소 · 측정 파일 · 열쇠는 보지 않는다)
- 판정: 묶음마다 (R5 평균 − 기준선 평균) → 그 평균과 승 · 무 · 패. 회귀 없음 = 평균 차이 ≥ 0. 평가자 일치도 = 같은 곡에서 두 점수 차가 1 이하인 비율
- 한계: 기준선은 101자리에 고유 26곡이라 같은 곡이 여러 묶음에 되풀이된다. 버전 표기(기준선에는 라이브 · 버스킹판이 섞임)나 곡 성향(기준선 곡의 58%는 Last.fm 유사곡)으로도 출처를 짐작할 수 있다. 사용자는 운영자라 지금 서비스의 곡을 알아볼 수도 있다 → Claude 점수를 같이 본다
- 실행 (`apps/backend`에서): `node scripts/eval/blind-sheet.cjs make --target <R5 폴더>` → `blind/sheet.csv`를 복사해 `scores-user.csv`로 저장하고 점수 · 모름 칸을 채운다 → `node scripts/eval/blind-sheet.cjs summary --target <R5 폴더>`(`blind/summary.md`)

점수 기준 — "이 글을 쓴 사람에게 이 모드로 이 곡을 틀어 준다면". 심취 = 지금 감정에 더 깊이 머물게 하는 곡, 완화 = 그 감정에서 부드럽게 빠져나오게 하는 곡(운영 프롬프트의 모드 정의)

| 점수 | 뜻                                                                    | 예: "오래 키운 강아지가 오늘 무지개다리를 건넜어" |
| ---- | --------------------------------------------------------------------- | ------------------------------------------------- |
| 5    | 글의 상황 · 감정과 모드 의도에 딱 맞는다 — 이 글이라서 고른 곡 같다   | 심취: 떠나보낸 존재를 그리는 곡                   |
| 4    | 감정과 모드 방향은 맞지만 이 글만의 상황까지는 아니다                 | 심취: 일반적인 슬픈 발라드                        |
| 3    | 거슬리지 않지만 이 글과 특별한 관련이 없다 — 어느 글에나 나올 법한 곡 | 무난한 어쿠스틱 팝                                |
| 2    | 감정이나 모드 방향 중 하나가 어긋난다                                 | 완화에 더 깊이 가라앉히는 곡 · 심취에 밝은 곡     |
| 1    | 반대로 작용한다                                                       | 어느 모드든 신나는 파티 곡                        |

- 곡 자체의 무드로 판단한다(아티스트의 대표 스타일이 아니라). 모르는 곡은 링크로 들어 보고, 그래도 어려우면 "모름"(평균에서 뺀다)
- 버전(라이브 등)은 보이는 그대로 매긴다. 어느 쪽 곡인지 추측하지 않는다

## 산출물 — `docs/measurements/<날짜>-<라벨>/`

- `meta.json`: 커밋 해시, Node 버전, 모델, 시작·종료 시각, 옵션
- `raw.jsonl`: 요청 1건 = 1줄 (입력 · LLM 출력 · 단계 추적 · 최종 곡 · 호출 집계 · 지연)
- `summary.md`: 요약 스크립트 출력
- 저장 범위: iTunes는 메타데이터만 저장, 미리듣기 오디오는 저장하지 않는다(약관)
- Last.fm 응답 내용(유사곡의 가수·곡명·유사도)은 저장소에 올리지 않는다. 공개 저장소에 올리면 제3자에게 제공하는 셈이라 Last.fm API 약관 4.3.3(제3자 재라이선스 금지)에 걸린다. 원본은 로컬에만 둔다(비상업·100MB 한도, 4.3.4)
  - `2026-11-02-baseline/raw.jsonl`은 이 내용을 뺀 버전이다: `candidates` 삭제, `resolve.*.resolved[].match` 삭제, LLM 시드가 아닌 `resolveCalls`의 가수·곡명은 `null`. 이 파일로 `summary.md`를 다시 만들면 원본과 같다
  - 기준선 하네스는 원본 필드를 기록하므로, 커밋 `56dd4dd`에서 다시 측정하면 커밋 전에 같은 정리를 거친다
